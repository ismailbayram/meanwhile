# waitgame — Design

> **Historical record.** Superseded in part by [2026-09-02-multi-agent-and-language-design.md](2026-09-02-multi-agent-and-language-design.md), which removed the "spot the bug" mutant cards described below (0.2.0), added Codex and Cursor alongside Claude Code, and gave the pool a `language` field; everything else here still describes the design as built.

**Date:** 2026-08-28
**Status:** Approved design, not yet implemented
**Repository:** standalone open-source repo (`~/python/waitgame`), distributed as a Claude Code plugin

## Problem

While Claude Code works on a task, the developer waits — often 10-15 minutes. The wait is not merely boring: attention drifts to unrelated tabs, and when the diff finally arrives the developer no longer holds the task's context. Reviewing it then costs a second, slower context load, and shallow reviews slip through.

The goal is not entertainment. The goal is to keep the developer's working memory loaded with the repository they are about to review.

## Success criteria

- The game starts and stops on its own, driven by whether Claude is busy. The developer never manages it.
- Playing requires no network call, no LLM call, and no measurable latency once the content pool exists.
- Every question comes from the developer's own repository. Generic trivia is out of scope.
- Content generation happens exactly once per explicit command, never in the background.
- Installing the plugin and running one command is the entire setup.

## Constraints discovered

**Claude Code's prompt does not accept input while Claude is working** — keystrokes are queued as the next prompt. The game therefore cannot live inside the Claude Code TUI, and cannot be a slash command played during the wait. It must be a separate process on a separate terminal pane.

**Question generation needs an LLM, but the wait is the worst time to call one.** A second LLM call while Claude is already working adds latency and cost precisely when the developer wants an instant answer. Generation is therefore separated in time from play.

## Architecture

Three parts, coupled only through two files on disk. No part imports another; each is testable alone.

```
/waitgame-build  (slash command, runs Claude)
        │  writes
        ▼
   .waitgame/pool.json          ← committed to the repo, shared by the team
        │  reads
        ▼
   waitgame TUI  ──watches──►  ~/.waitgame/state/<project-hash>.json
   (uvx, separate pane)                    ▲
                                           │ writes
                              hooks: UserPromptSubmit / Stop
```

### Part 1 — `/waitgame-build` (content generation)

A slash command shipped by the plugin. It reads the repository — models, serializers, route and endpoint definitions, the README, the CHANGELOG, and recent `git log` output — and produces the full content pool in one pass, writing `.waitgame/pool.json`.

It generates both content types:

- **Quiz items**: multiple-choice questions about the project's domain and features, phrased the way a project manager would ask them ("what does `Category.passport_groups` do?"). Each carries a one-line explanation and the source file it came from.
- **Mutant items**: a real snippet from the repository with a single operator or condition altered (`<` → `<=`, `and` → `or`, a dropped `not`, an inverted early return). The player decides whether the snippet is correct or bugged, and the item carries the explanation.

**Mutants are generated by the LLM, not by a parser.** This is the decision that keeps the tool language-agnostic: no AST module per language, no tree-sitter grammar matrix, no build step for WASM parsers. Python, Go, Rust, TypeScript, or anything else works identically, because the only component that understands code runs at build time and is Claude itself.

Roughly a third of mutant items are emitted unmutated (`clean: true`) so that "looks fine to me" stays a real answer rather than a losing one.

The command is the only part of the system that costs tokens. It runs when the developer asks, never on a timer and never in the background.

### Part 2 — hooks (busy/idle signal)

Two hook entries shipped in the plugin's `hooks/hooks.json`, both pointing at one short shell script:

- `UserPromptSubmit` → write `{"status": "busy", "ts": <epoch>}`
- `Stop` → write `{"status": "idle", "ts": <epoch>}`

The file lives at `~/.waitgame/state/<sha256 of cwd>.json`, outside the repository, because it is machine-local runtime state. The script does nothing else: no parsing, no network, no output on stdout (which would otherwise be injected into Claude's context).

This was chosen over tailing the session `.jsonl` transcript. The transcript approach needs no hook installation, but it infers "still thinking" from file mtime — a heuristic that misreads long tool calls — and it breaks whenever the log format changes. Since the tool is a plugin already, and plugins ship hooks, the exact signal is free.

### Part 3 — `waitgame` TUI (the player)

A Python terminal app, run as `uvx waitgame` in a second pane (tmux split, iTerm pane, or a plain second window). It watches the state file, and:

- on `busy`: wakes, loads `.waitgame/pool.json` from the current directory, and serves cards one at a time, tracking a streak counter for the session
- on `idle`: freezes the current card and prints `Claude is done ↑`, so the developer's eye returns to the other pane

The TUI makes **zero LLM calls and parses no source code**. It reads two JSON files and renders cards. That is the whole of it, and it is why the interactive path has no latency and no cost.

## Data format

`.waitgame/pool.json`, committed to the repository so a team shares one pool:

```json
{
  "builtAt": "2026-08-28",
  "headSha": "3b7278e",
  "repo": "trumy",
  "items": [
    {
      "type": "quiz",
      "q": "What is Category.passport_groups for?",
      "choices": ["Tags a category for search", "Binds passport groups to a category", "Stores category images"],
      "answer": 1,
      "why": "Links passport groups to the category so eligibility can be resolved per category.",
      "source": "apps/products/models.py"
    },
    {
      "type": "mutant",
      "lang": "python",
      "snippet": "if user.consent_version < CURRENT:\n    flag(user)",
      "clean": false,
      "bug": "Should be `!=`; users on a newer version are never flagged.",
      "source": "apps/users/api/services.py"
    }
  ]
}
```

Mutant items store the **snippet text, never a line number**. Line numbers rot on the next commit; a snippet stays readable and self-contained even when the file it came from has moved on.

## Staleness

`pool.json` records the `headSha` it was built from. On startup the TUI runs `git rev-list --count <headSha>..HEAD`. Past a threshold (default 50 commits, configurable) it shows a banner:

> pool is N commits behind — run /waitgame-build

It never regenerates on its own. Silent background generation would burn tokens the developer did not ask for, and is the failure mode this design exists to avoid.

If `pool.json` is missing entirely, the TUI prints the build instruction and exits rather than falling back to generic questions.

## Scoring

Score and streak are written to `.waitgame/scores.json`, which is **gitignored**. Scores are per-developer and local. The plugin's install instructions add the entry to `.gitignore`.

## Testing

- **Hooks**: shell-level test — invoke the script, assert the state file's content and path. No Claude Code needed.
- **TUI**: the card/score/streak logic is pure functions over a pool object and a state object; tested with fixture JSON, no filesystem watching and no terminal in the loop. The watcher layer is a thin shell around them.
- **Build command**: the output is LLM-generated, so it is validated against the schema — required fields present, `answer` in range for the choice count, every `source` path existing in the repo — not against expected content.

## Packaging

- Plugin name: `waitgame`; PyPI package: `claude-waitgame` (invoked as `uvx claude-waitgame`).
- Python, not Go or Node: `uvx` runs the published package without an install step, and there is no cross-platform build matrix to maintain. The TUI does no heavy work, so runtime cost is irrelevant. `textual` provides the terminal UI.
- The repository holds both the plugin manifest (`.claude-plugin/plugin.json`, `commands/`, `hooks/`) and the Python package, so one clone and one marketplace entry cover the whole tool.

## Out of scope for v1 (YAGNI)

Leaderboards, accounts, team score sync, multiplayer, difficulty tiers, sound, and a browser UI are all excluded. They add a server, state sync, or a second window — none of which serve the one thing this tool does.

**Diff prediction** ("guess which files Claude will touch", auto-scored when the diff lands) was considered and deliberately deferred. It measures scope retention most directly of all the mechanics and costs nothing to generate, but it needs post-run diff inspection, which is a second integration. It is the first candidate for v2.
